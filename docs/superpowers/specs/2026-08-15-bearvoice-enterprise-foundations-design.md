# BearVoice 企业私有化产品机会平台设计规格

> 状态：已实施，并于 2026-08-15 完成首轮系统架构审查与硬化
> 日期：2026-08-15
> 适用对象：小熊电器客服运营、产品经理、品控团队、管理层与系统管理员

## 1. 决策与定位

BearVoice 的产品终点不是聚类图表或自动报告，而是一个可被审核、认领、验证和追踪的“产品机会”。平台把分散的客户原声转化为两类决策对象：现有 SKU 的可执行改进机会，以及有证据支撑的未满足需求或新品概念。

本系统按小熊电器内部单企业、私有化部署设计。它不建设多租户 SaaS、公开注册、计费或客户自助管理能力；仍按部门、产品线和角色实施数据访问控制。

长期目标是形成三个闭环：

1. **证据闭环**：数据源 → 原始原声 → 多信号抽取 → 聚类 → 原话证据。
2. **决策闭环**：产品机会 → 人工审核 → 竞品验证 → 负责人和状态 → 执行结果。
3. **学习闭环**：审核与结果 → 黄金样本 → 模型回归 → 版本发布或回退。

## 2. 设计目标

本轮设计必须同时满足以下目标：

- 复用养生壶 370 条已去重原声、10 个既有抽取缓存、现有聚类和建议，不重复调用抽取模型。
- 建立可扩展到多渠道、多产品、多时间批次的统一数据模型。
- 任何聚类、机会和建议均可下钻到脱敏原声、来源、日期和分析版本。
- 允许一段对话包含多个信号，保留低置信度、异常项和未归类项。
- AI 输出先进入人工审核，不直接成为企业产品结论。
- 聚类改名、合并、拆分、接受和驳回形成新修订，不覆盖历史运行结果。
- 用真实中文咨询建立人工定标与回归评测工作区。
- 提供赛事决策视图和企业运营工作台，两者使用同一数据与权限体系。
- 所有模型、提示词、数据集和代码版本均可追踪、比较和回退。
- 私有化环境默认不向外部模型发送数据；只有管理员配置并批准的模型提供商可被调用。

## 3. 明确不做

- 不建设多租户 SaaS、计费、套餐或公开用户体系。
- 不自建淘宝、京东反爬链路；本轮只实现文件导入和数据源适配接口。
- 不把 3 天、单渠道样本解释为趋势或因果结果。
- 不用好评率、情绪或词云代替产品机会判断。
- 不把咨询量或用户投票作为唯一优先级。
- 不自动批准产品结论，不替代产品、品控或工程负责人签字。
- 不完成 BOM、模具、定价等新品商业可行性论证。
- 不直接复制 AGPL 项目代码；仅借鉴可验证的架构和工作流思想。

## 4. 用户与职责

| 角色 | 核心任务 | 数据范围 | 关键权限 |
|---|---|---|---|
| 客服数据运营 | 导入、检查和治理原声数据 | 授权渠道和产品线 | 创建批次、处理隔离数据、查看来源健康度 |
| 客服主管 | 发现重复咨询和话务驱动因素 | 所属业务范围 | 查看聚类、补充业务解释、发起机会审核 |
| 产品经理 | 判断是否形成产品机会 | 所属产品线 | 接受、修改、驳回、认领和推进机会 |
| 品控人员 | 处理缺陷、安全与质量信号 | 授权产品线 | 提升安全优先级、发起复核、记录质量结论 |
| 管理层 | 跨产品查看机会组合与执行状态 | 汇总授权范围 | 查看决策驾驶舱，不修改原始证据 |
| 系统管理员 | 管理身份、数据源、模型和系统策略 | 全局管理元数据 | 配置 OIDC、模型提供商、权限和保留策略 |
| 模型审核员 | 建立黄金样本并发布模型版本 | 脱敏评测数据 | 审核样本、运行评测、批准或回退版本 |

原始证据不可由任何业务角色修改。纠错通过补充标记或新版本完成，并保留审计记录。

## 5. 总体架构

### 5.1 技术选择

- **前端**：React、TypeScript、Vite、TanStack Query、Apache ECharts。
- **业务 API**：FastAPI、Pydantic、SQLAlchemy 2、Alembic。
- **主数据存储**：PostgreSQL 16；向量能力由 pgvector 提供。
- **耐久工作流**：Temporal Server 与 Python Worker。
- **缓存与限流**：Redis；不承担主流程唯一状态源。
- **对象存储**：S3 兼容接口；部署时连接企业批准的对象存储。
- **身份与权限**：企业 OIDC；可对接 Keycloak 或现有统一身份平台。
- **模型治理**：内部分析运行记录为权威账本，同时通过 OpenTelemetry 接入自托管 Langfuse 或企业可观测平台。
- **部署**：本地开发使用 Docker Compose；生产以 Kubernetes/Helm 为目标部署方式。

### 5.2 模块化单体边界

后端首先作为一个可部署单元，但代码和数据库边界按领域模块组织：

1. `identity`：身份、角色、部门、产品线数据范围。
2. `sources`：数据源、导入批次、游标和来源健康度。
3. `evidence`：原声、对话轮次、脱敏结果和证据引用。
4. `analysis`：抽取、向量、聚类、分类法和运行版本。
5. `opportunities`：产品机会、竞品证据、负责人和执行状态。
6. `review`：人工审核、聚类修订、争议和审计。
7. `evaluation`：黄金样本、评测运行、版本门禁和回退。
8. `reporting`：赛事视图、企业驾驶舱、导出和快照。

模块通过应用服务和领域事件通信，不允许跨模块直接修改内部表。只有出现真实的独立扩缩容、故障隔离或组织所有权需求时，才拆分为独立服务。

## 6. 核心数据模型

### 6.1 来源与原声

| 实体 | 关键字段与约束 |
|---|---|
| `Source` | 类型、名称、渠道、连接状态、授权范围、最后成功时间、最后错误；不保存明文密钥 |
| `IngestionBatch` | 来源、文件哈希、时间范围、原始条数、去重条数、隔离条数、状态和操作者 |
| `VoiceRecord` | 稳定 ID、来源外部 ID、产品、SKU、渠道、发生时间、原始对象引用、规范化文本、内容哈希、脱敏状态 |
| `ConversationTurn` | 所属原声、轮次、说话方、规范化文本、脱敏文本和顺序 |
| `PrivacyFinding` | 实体类型、位置、识别器、置信度、处理动作和审核状态；不重复保存未脱敏值 |

`VoiceRecord` 只追加或做纠错版本，不被分析任务覆盖。相同来源与外部 ID 必须幂等；缺少外部 ID 时使用规范化内容哈希和来源范围生成去重键。

### 6.2 分析与分类法

| 实体 | 关键字段与约束 |
|---|---|
| `AnalysisRun` | 数据集哈希、代码版本、模型版本、提示词版本、参数、阶段状态、耗时、成本、错误和父运行 |
| `Signal` | 原声、信号类型、阶段、对象、问题表述、隐含需求、证据片段、抽取置信度和模型来源 |
| `Embedding` | 对象类型、对象 ID、模型、维度、内容哈希和向量；相同哈希与模型复用 |
| `TaxonomyVersion` | 产品范围、父版本、创建来源、状态和发布人 |
| `Cluster` | 原始名称、当前名称、说明、主信号、关键词、代表原声、异常标记和状态 |
| `ClusterMembership` | 聚类、原声或信号、距离、置信度、是否异常、分配来源和人工覆盖标记 |
| `TaxonomyRevision` | 改名、合并、拆分、移出、恢复等操作，包含理由、操作者和前后映射 |

一条原声可产生多个 `Signal`，一个信号在同一分类法版本中最多有一个主聚类，也可处于异常或待归类状态。置信度只在有校准依据时展示；无法校准的历史结果标记为“未校准”，不伪造小数分值。

### 6.3 产品机会与执行结果

| 实体 | 关键字段与约束 |
|---|---|
| `Opportunity` | 类型、标题、问题、场景、人群、产品/SKU/部件、影响面、严重度、安全等级、差异化、建议动作和状态 |
| `OpportunityEvidence` | 机会、原声或信号、证据角色、引用片段、支持/反对方向、独立用户键和证据有效性 |
| `ReviewDecision` | 对象、决定、理由、审核人、审核版本、时间和替代意见 |
| `CompetitorEvidence` | 机会、竞品、来源 URL/文件、采集时间、引用片段、可比维度、证据强度和审核状态 |
| `ActionItem` | 负责人、协作部门、目标、截止时间、状态、外部系统引用和决策理由 |
| `OutcomeMeasurement` | 行动、指标定义、基线、观察窗口、结果、限制和证据等级 |

机会状态固定为：`draft`、`pending_review`、`accepted`、`rejected`、`validating`、`planned`、`in_progress`、`completed`、`archived`。任何状态变化写入不可变审计事件。

改进型机会至少需要 3 条经审核的独立原声证据；新品型机会至少需要 5 条经审核、覆盖不同人群或场景的独立原声证据。系统可生成候选，但只有满足门槛并通过人工审核后才可进入 `accepted`。

### 6.4 评测与审计

| 实体 | 关键字段与约束 |
|---|---|
| `GoldenExample` | 脱敏输入、预期信号、预期对象、证据范围、难例标签、审核人和争议状态 |
| `EvaluationRun` | 候选版本、黄金集版本、各项指标、分层结果、失败样本和发布结论 |
| `ModelRelease` | 模型、提示词、规则、批准人、门禁结果、启用时间和回退目标 |
| `AuditEvent` | 操作者、动作、对象、前后摘要、关联运行、时间和请求追踪 ID |

审计事件不得记录密钥、未脱敏个人信息或完整模型提示内容中的敏感数据。

## 7. 端到端工作流

### 7.1 导入与隐私门禁

1. 操作者登记数据源并上传文件或触发适配器。
2. 系统计算文件哈希，识别已处理批次并保证幂等。
3. 校验编码、字段、时间、产品和记录粒度；不合格记录进入隔离区，不阻塞合格记录。
4. 按来源外部 ID 去重；无外部 ID 时使用内容哈希去重。
5. 只在隔离环境读取原始文本，执行规则、识别器和人工抽样复核。
6. 脱敏通过后创建 `VoiceRecord`；原文件进入受控对象存储并按保留策略管理。

### 7.2 分析运行

1. 创建含数据集哈希和版本信息的 `AnalysisRun`。
2. 复用相同内容哈希、模型和提示词版本的抽取或向量缓存。
3. 对每段原声抽取零到多个信号，并保存直接证据片段。
4. 生成向量并形成候选聚类；保留异常项和待归类项。
5. LLM只负责聚类名称、根因解释和机会草案，不覆盖算法成员关系。
6. 执行结构校验、证据引用校验、覆盖率检查和安全规则。
7. 生成待审核分类法和待审核机会，不直接发布企业结论。

### 7.3 人工治理与机会发布

1. 审核员查看候选聚类、代表原声、边界样本和异常项。
2. 审核员可改名、合并、拆分、移出或恢复；系统记录修订而非修改原运行。
3. 产品经理或品控审核机会的证据、动作、严重度和优先级。
4. 安全类机会绕过常规频次排序，进入品控复核队列。
5. 满足证据门槛并通过审核的机会进入 `accepted`，否则保持草案或被驳回。
6. 竞品证据作为具体机会的验证层加入，不生成脱离机会的竞品全景报告。

### 7.4 执行与学习

1. 被接受机会分配负责人和截止时间，可关联企业项目管理或 PLM 编号。
2. 执行结果回写机会，保留未执行和驳回原因。
3. 高价值人工修订进入黄金样本候选，由模型审核员批准。
4. 新模型或提示词必须在冻结黄金集上回归，满足门禁后才能发布。
5. 发布后按产品线、信号类型和难例分层监控；退化时回退到上一个批准版本。

## 8. 耐久性与错误处理

Temporal 工作流为每个导入批次和分析运行保存可恢复状态。活动必须幂等，外部模型调用使用运行 ID、阶段和输入哈希作为幂等键。

错误按以下方式处理：

- 单条记录格式错误：隔离该记录并继续批次。
- 单个来源失败：标记来源健康度，不影响其他来源。
- 模型临时失败：按提供商策略退避重试；超过次数后暂停运行并保留已完成阶段。
- 模型输出不符合结构：保存诊断摘要，进入失败队列，不用默认值冒充成功。
- 服务重启：由 Temporal 从已确认阶段恢复，不重新执行已缓存抽取。
- 人工审核超时：保持 `pending_review` 并提醒，不自动接受。
- 权限不足：拒绝请求并记录安全审计，不暴露对象是否存在。
- 竞品来源失效：保留历史快照和失效状态，不静默删除证据。

每个失败记录机器可读的阶段、错误码、提供商、模型、重试次数、耗时和关联运行；错误正文在写入前移除密钥和个人信息。

## 9. 产品界面与信息架构

### 9.1 赛事决策视图

默认使用养生壶真实数据，首屏直接回答：

- 分析了什么：数据来源、日期、去重后样本和边界。
- 发现了什么：四类信号构成、Top 反馈类型和异常项。
- 为什么值得做：影响面、安全风险、实施难度和证据强度。
- 下一步是什么：至少 3 条可落地机会及负责人或待审核状态。

现场演示可从机会卡片下钻到脱敏原声，再打开该机会的工作流时间线，完整覆盖赛题 A、B、C。基础设施拓扑不放在第一屏。

### 9.2 企业运营工作台

导航固定为：

1. **决策驾驶舱**：机会组合、状态、产品线、类型和安全提醒。
2. **原声数据**：来源、批次、数据质量、隔离记录和覆盖范围。
3. **聚类治理**：分类法、聚类、异常项、改名、合并与拆分。
4. **机会中心**：证据、反例、竞品验证、审核、负责人和行动。
5. **质量中心**：黄金集、评测对比、失败样本、版本发布和回退。
6. **系统管理**：身份、权限、数据源、模型、保留策略和审计。

### 9.3 可视化原则

- KPI 卡展示样本量、有效机会、待审核、安全提醒和证据覆盖，不把不同口径指标放在同一排名中。
- Top 类别使用从零起点的横向排序条形图，显示条数、占比、样本分母和时间范围。
- 信号构成使用 100% 堆叠条或紧凑构成图，同时给出绝对条数。
- 机会优先级用矩阵或分组列表展示影响面、严重度、成本和安全覆盖，不用咨询量单维排序。
- 只有积累足够时间跨度后才展示趋势；当前 3 天样本只做截面分析。
- 图表使用中性标题、直接标签和色彩以外的状态编码，保证移动端与灰度可读。
- 所有图表可下钻到证据表；图表与表格使用同一聚合查询，数字必须对账。

## 10. 模型与分析方法

分析采用“确定性处理 + 向量候选 + LLM解释 + 人工治理”：

- 确定性层负责编码、字段、去重、脱敏、计数、约束和证据引用完整性。
- 信号抽取允许多标签，提示词将用户文本视为数据而非指令，并要求直接证据片段。
- 向量和聚类算法生成候选成员关系、代表样本和异常项。
- LLM生成聚类名称、根因说明和机会草案，但不独占聚类决策。
- 人工审核形成可发布分类法、机会和黄金样本。

历史 Claude 缓存以 `legacy-claude-cache` 提供商和明确的旧提示词版本导入。无法恢复的置信度记为未校准；不得从成员距离或情感分布伪造置信度。

## 11. 黄金样本与发布门禁

首个评测集从养生壶 370 条中分层抽取 100 条，覆盖四类信号、10 个既有聚类、多轮对话、安全问题、边界样本和纯咨询。样本初始状态为“待人工定标”，不得把现有模型结果当作黄金答案。

每条样本由两名业务审核者独立判断；分歧进入仲裁。首轮记录以下基线：

- 信号、对象和问题表述的一致率；
- 直接证据是否支持抽取和机会；
- 安全类信号漏检；
- 聚类覆盖、异常项和重复机会；
- 机会接受、轻微修改、重大修改和驳回原因；
- 完成一次审核和形成决策所需时间。

确定性门禁：

- 报告和机会中的证据引用必须 100% 可解析回受控原声记录。
- 测试导出中不允许出现已定义的个人信息泄漏。
- 聚类成员不能静默遗漏或重复计入同一主分类法版本。
- 新模型不得破坏已批准的安全类黄金样本；任何退化都阻止发布。

业务接受率和时间节省门槛在取得人工基线后由产品与品控负责人共同冻结，不在无基线时伪造目标值。

## 12. 赛事与长期价值的共同验收

### 12.1 赛事验收

- A：可展示养生壶 Top 反馈类型、占比、分母和数据边界。
- B：至少 3 条已具备证据、优先级和具体动作的改进机会。
- C：可演示从数据导入、抽取、聚类、审核到机会发布的工作流及失败恢复点。
- 现场可从每条机会下钻到脱敏原声和运行版本。

### 12.2 企业可行性验收

- 同一批数据重复导入不产生重复原声或重复分析任务。
- 已完成的抽取可按内容哈希和版本复用。
- 聚类治理产生可追踪的新修订，历史结果保持可查询。
- 权限测试证明不同角色只能访问授权产品线和操作。
- 模型或提示词版本变更可比较、阻止退化并回退。
- 机会可被接受、驳回、认领和推进，并保留完整审计历史。
- 现有 Markdown 报告继续可生成，数字与企业工作台对账。

企业影响仍需受控试点验证。本轮只能证明数据链、工作流和审核机制可行，不能声称已经提升产品决策、降低客服量或改善质量。

## 13. 本轮实施边界

本轮不是临时 Demo，而是在目标架构上贯通一条真实纵向链路：

1. 建立前后端、数据库、耐久工作流和身份权限骨架。
2. 实现统一数据模型和数据库迁移。
3. 导入现有养生壶数据、10 个抽取缓存、聚类和建议，形成可追踪历史运行。
4. 实现证据下钻、聚类治理、机会审核和状态流转。
5. 生成 100 条待人工定标样本并实现评测运行框架。
6. 实现赛事决策视图和企业运营工作台的核心页面。
7. 保留现有命令行和 Markdown 报告，新增结果必须与其对账。
8. 完成单元、集成、权限、工作流恢复和关键界面端到端测试。

以下只建立扩展接口，不在本轮接通：企业正式 SSO、生产 Kubernetes 集群、PLM/项目管理写回、更多电商平台数据、自动竞品采集和新品商业论证。

## 14. 测试与验证策略

- **后端单元测试**：领域状态、证据门槛、去重、权限、版本和修订规则。
- **工作流测试**：重试、暂停、恢复、幂等、缓存复用和人工审核等待。
- **数据库集成测试**：迁移、唯一约束、事务、pgvector查询和审计不可变性。
- **前端单元测试**：筛选、状态、图表数据转换和权限可见性。
- **端到端测试**：导入养生壶 → 查看聚类 → 审核机会 → 下钻证据 → 导出报告。
- **数据对账**：370 条原声、254 条改进信号、10 个聚类和 9 条现有建议作为迁移基准，不把这些历史结果当成新模型准确性证明。
- **视觉验证**：在桌面和移动宽度检查标题、标签、长类名、证据抽屉、对比度、灰度和打印输出。
- **安全验证**：未授权访问、越权产品线、提示注入文本、上传文件、日志泄密和导出脱敏。

所有新行为遵循测试先行。每个逻辑单元先产生可解释的失败测试，再写最小实现，最后运行全量回归和最终场景验证。

## 15. 关键决策记录

| 决策 | 选择 | 原因 |
|---|---|---|
| 产品终点 | 产品机会及执行闭环 | 报告本身不产生企业决策价值 |
| 部署模型 | 单企业私有化 | 用户已明确小熊内部长期使用 |
| 服务形态 | 模块化单体 | 保持领域边界，同时避免在边界未验证前拆服务 |
| 主流程 | Temporal 耐久工作流 | 支持长任务、人工暂停、恢复、重试和运行历史 |
| 数据库 | PostgreSQL + pgvector | 业务事务、证据关系和向量检索共用一致数据层 |
| AI决策 | 候选生成，人工发布 | 产品与质量结论必须由可追责人员确认 |
| 展示策略 | 赛事视图 + 企业工作台 | 同一产品同时满足现场表达和长期运营 |
| 竞品分析 | 绑定具体机会 | 避免脱离决策的竞品全景报告 |
| 首条链路 | 养生壶历史结果迁移 | 复用已验证缓存，避免重复抽取并提供真实对账基线 |
