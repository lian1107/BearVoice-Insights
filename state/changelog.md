# 小熊电器客户原声分析与产品改进挖掘 · 演化记录（给人类）

> 每条只答三问：**变了什么 · 为什么变 · 对你意味着什么**。每里程碑一条，倒序追加；细节见 `state/board.md` 与 git log。

## 2026-08-15 · 可追溯的机会决策与行动闭环

**变了什么**：新增不可变分类法修订、机会证据门槛与人工审核、安全优先级覆盖、行动负责人和结果/局限回收，所有关键决定均生成审计事件。

**为什么变**：企业长期使用不能只给出一次性排名；分析口径要能复现，机会要能说清证据和决策理由，行动要能验证是否真正改善。

**对你意味着什么**：小熊内部可在同一系统中从原声证据追到机会审核、执行负责人和实际结果；安全风险不会被低声量埋没，也不会绕过人审。

## 2026-08-15 · 可恢复且有人审的分析工作流

**变了什么**：新增 Temporal 九阶段耐久工作流、失败重试幂等键、人工审核暂停/恢复信号，以及结构化且先脱敏的失败诊断与最小追踪属性。

**为什么变**：企业分析任务可能中断、重试或等待跨部门审核，不能依赖一次进程跑到底，也不能为排障把客户原文、提示词或凭据写进日志。

**对你意味着什么**：长任务中断后可从已完成阶段继续，抽取失败不会换一套输入重复记账；分类法发布前始终保留明确的人审关口。

## 2026-08-15 · 养生壶验证基线进入平台

**变了什么**：10 个既有抽取缓存以严格只读模式迁入平台数据库，对账得到 370 条原声、370 条信号、254 条可行动信号、10 个聚类和 9 条待审核机会；CSV 接入同时固化了去重、隐私门禁和幂等协议。

**为什么变**：既有结果是节省重复抽取成本的验证基线，但不能因为缓存缺失静默调用模型，也不能把地址等个人信息带入长期数据资产。

**对你意味着什么**：平台已有真实养生壶证据可继续做聚类治理和机会决策；重复迁移不会重复记账，缓存不完整时会明确停止，而不是产生一套来源不明的新结果。

## 2026-08-15 · 企业领域与数据库真相源

**变了什么**：用 PostgreSQL/pgvector 和 Alembic 建立 22 张统一核心表，覆盖从数据来源、原声和多信号，到分类法、产品机会、竞品证据、执行结果、黄金样本和审计事件的全链路。

**为什么变**：长期使用不能让 Markdown 报告或一次性脚本成为事实正本；领域规则、数据库约束和可回退迁移必须共同定义唯一真相源。

**对你意味着什么**：后续养生壶历史结果和未来淘宝等来源将进入同一证据模型，可被下钻、复核和持续迭代，而不是各自生成无法对账的报告。

## 2026-08-15 · 企业平台可重复运行骨架

**变了什么**：新增经批准的 `platform/` 顶层协议，建立锁定依赖的 FastAPI 后端、React 前端、非 root 生产镜像与 PostgreSQL/pgvector、Valkey、Temporal 的本地私有化编排；模型外发默认关闭。

**为什么变**：长期企业平台必须先有可复现、可测试、默认不外发数据的运行地基，后续的数据治理、机会审核和评测闭环才能建立在同一真相源上。

**对你意味着什么**：平台已从设计进入可运行实施；本机可构建并启动前后端生产镜像，下一里程碑将把统一领域模型和数据库迁移接入这套骨架。

## 2026-08-15 · 企业私有化五项地基设计

**变了什么**：平台定位从一次性原声分析和报告，升级为小熊内部私有化的产品机会决策平台；设计规格统一了证据、分析、审核、机会、执行和模型评测闭环。

**为什么变**：赛题要求场景价值、AI 应用深度和落地潜力，长期企业价值也取决于机会能否被审核、认领和验证，而不是图表或报告数量。

**对你意味着什么**：后续不另做临时 Demo；在企业目标架构上先贯通养生壶真实链路，书面规格经人复核后再进入测试驱动实施。

## 2026-08-15 · 养生壶首份分析报告

**变了什么**：复用 Claude 已完成的 370 条抽取缓存，由 Codex 接续完成 10 类聚类、9 条改进建议和首份报告；新增重复口径与地址证据过滤回归测试。

**为什么变**：Claude 在聚类阶段因认证失效中断，且原报告生成逻辑混淆了重复 ID 与重复行，并漏过一段地址型文本。

**对你意味着什么**：赛题成果 A、B 和命令行工作流 C 已有一套可复核样稿；先核查玻璃炸裂安全项和聚类口径，再决定是否扩展到其余 4 个品类。
